## RLS fix for the exposed production tables (2026-11-15): written and tested, NOT on production
**Problem (read-only checks on production):** 117 of 314 `public` tables have RLS off, and `anon`/`authenticated` hold full privileges on them, so anyone with the public key can read and write them. Only `admin_analytics_events` (76,232 rows) and `app_migration_metadata` (5) hold data. Pre-checks also found (1) 54 policies already written on these tables (own-row and admin rules) that do nothing until RLS is on, and (2) a view, `user_api_keys_read`, that runs as its owner (ignores RLS) and returns DECRYPTED API keys, readable by anon. The base table is empty, so nothing has leaked.
**Migration `20261120000000_enable_rls_on_exposed_tables.sql`** (generic, idempotent):
1. Enables RLS on every exposed table, so the existing own-row/admin policies start to apply.
2. Removes TRUNCATE/REFERENCES/TRIGGER from anon/authenticated on them (defence in depth: PostgREST has no TRUNCATE verb).
3. On tables with no policy at all, also removes INSERT/UPDATE/DELETE. Tables that have policies keep their write grants so their own policies can work. SELECT stays, so readers get an empty result rather than an error.
4. Makes `user_api_keys_read` `security_invoker` and takes it away from anon.
5. Keeps the live write path: `admin_analytics_events` accepts INSERT from `anon` (all 146 daily POSTs arrive with the anon role; insert-only, no read/update/delete). Note this open insert lets anyone add analytics rows; a better design is for that edge function to use the service role.
**Tested:** 26 SQL assertions on a throwaway local Postgres (`supabase/tests/run-enable-rls-assertions.sh`; includes the keys-view hole before and after, own-row policies working, forged-owner insert refused, truncate refused), 9 mutations caught, and the same behaviour confirmed on the real Supabase validation branch with stand-in tables, policies and view (removed afterwards).
**Not proven:** the branch lacks the real 117 tables, so the real effect on the other apps that share this database is untested. Policies that read `app_user_roles` (also exposed, empty) will see no rows once RLS is on, so only the `is_super_admin()` path grants admin access. Production still has the exposure until you approve a staged apply (view fix + deny-by-default tables first, then the tables with policies; watch the API logs after each).
Roll back: `alter table ... disable row level security` and re-GRANT.
