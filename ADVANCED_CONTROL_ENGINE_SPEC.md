# Advanced Control Engine Spec — SmartVideo

## 1. Purpose

Replace ad-hoc per-studio input plumbing with a single reusable control engine that maps any `Model.inputs` schema to rendered controls, validated state, and an API payload. The engine must work within the existing SmartVideo architecture: vanilla JS DOM manipulation, Tailwind CSS, no heavy framework dependencies.

## 2. Data Flow

```
Model (from catalog)
    │
    ▼
ModelInput  ← normalized per-field schema
    │
    ▼
ControlConfig  ← UI binding + metadata (defaults, min, max, step, options, tooltips,
                  validation rules, conditional visibility expressions)
    │
    ▼
ControlUI     ← DOM elements generated by ControlGenerator
    │
    ▼
ValidatedState  ← bound form state with live validation
    │
    ▼
ApiPayload      ← serialized request body (only parameters supported by the selected model)
```

## 3. Supported Input Types

| Engine type      | UI component                                  | Notes                                          |
|------------------|-----------------------------------------------|------------------------------------------------|
| `string`         | `<input type="text">` or `<textarea>`         | `multiline: true` → textarea                  |
| `text`           | `<input type="text">`                         | Short single-line string                       |
| `textarea`       | `<textarea rows="4">`                         | Multi-line text                                |
| `prompt`         | `<textarea rows="6" class="prompt-box">`      | Primary generation prompt; supports tokenization and examples |
| `number`         | `<input type="number">`                       | Float or integer; respect `step`               |
| `integer`        | `<input type="number" step="1">`              | Whole numbers only                             |
| `slider`         | `<input type="range">` + numeric display      | Requires `min`, `max`, `step`                  |
| `boolean`        | Toggle switch / checkbox                      |                                              |
| `select`         | `<select>`                                    | Requires `options` array                       |
| `enum`           | Button group or `<select>`                    | Requires `enum` array                          |
| `image`          | Upload dropzone + preview                     | Single image; `accept="image/*"`               |
| `image[]`        | Multi-image upload grid                      | Array of image URLs                            |
| `video`          | Upload dropzone + preview                     | `accept="video/*"`                             |
| `audio`          | Upload dropzone + preview                     | `accept="audio/*"`                             |
| `color`          | `<input type="color">` + hex input            |                                              |
| `aspect_ratio`   | Preset grid (e.g. 16:9, 9:16, 1:1)           | Computed from `enum`                           |
| `seed`           | Number input + dice-roll button               | `-1` means random; special handling           |
| `model_selector` | Model list + provider sidebar                 | Wired to `modelCatalog`                        |

## 4. Metadata Fields

Every `ControlConfig` may carry:

```typescript
type ControlMetadata = {
  default: string | number | boolean | string[];
  min?: number;
  max?: number;
  step?: number;
  options?: string[];         // for select / enum
  description?: string;       // rendered as help text or tooltip
  tooltip?: string;           // hover title
  placeholder?: string;
  required?: boolean;
  validation?: ValidationRule[];
  visibleWhen?: string;       // conditional visibility expression (see §6)
  disabledWhen?: string;      // conditional disable expression
  group?: string;             // logical grouping (e.g. "advanced", "lora")
  order?: number;             // render order within group
};
```

## 6. Conditional Visibility

Visibility and disabled-state are driven by expressions evaluated against the current `ValidatedState`. Expressions are simple strings parsed by a safe evaluator; no `eval()`.

### 6.1 Expression Grammar

```
<expr>      := <field> <op> <value>
<op>        := "==" | "!=" | ">" | "<" | ">=" | "<=" | "in" | "exists"
<value>     := <string> | <number> | <array>
<field>     := dot-separated path into ValidatedState.values
```

Examples:
- `model_id == "flux-dev"` — show only when Flux Dev is selected
- `seed exists` — show seed field only if the model schema declares a `seed` input
- `lora in ["flux-dev", "flux-schnell"]` — show LoRA only for specific models
- `image_mode == true` — show image upload only in I2I mode

### 6.2 Engine Behavior

```typescript
function evaluateVisibility(expression: string, state: ValidatedState): boolean {
  if (!expression) return true;
  // 1. Parse expression into AST (operator precedence: comparison only, no nesting)
  // 2. Resolve field path from state.values
  // 3. Apply operator
  // 4. Return boolean
}

function isControlVisible(config: ControlConfig, state: ValidatedState): boolean {
  return evaluateVisibility(config.metadata.visibleWhen || '', state);
}
```

### 6.3 Applied Examples

| Control              | visibleWhen expression         | Effect                                    |
|---------------------|-------------------------------|-------------------------------------------|
| `seed`              | `seed exists`                 | Hidden unless model.inputs declares seed  |
| `lora`              | `lora exists`                 | Hidden unless model.inputs declares lora  |
| `negative_prompt`   | `negative_prompt exists`      | Hidden unless model supports it            |
| `custom_width/height` | `resolution not in ["1K","2K","4K"]` | Show when resolution enum absent |
| `reference_strength` | `model_id == "flux-pulid"`    | Pulid-only parameter                       |

## 7. Control Generator Logic

### 7.1 Registry

A `ControlGenerator` class owns a registry mapping `ControlType` → render function. Each render function receives a `ControlConfig` and the current `ValidatedState`, and returns a `ControlUI`.

```typescript
export class ControlGenerator {
  private registry: Record<ControlType, ControlRenderer>;

  constructor() {
    this.registry = {
      text:          renderTextInput,
      textarea:      renderTextarea,
      prompt:        renderPromptInput,
      number:        renderNumberInput,
      integer:       renderIntegerInput,
      slider:        renderSlider,
      boolean:       renderBooleanToggle,
      select:        renderSelect,
      enum:          renderEnumGroup,
      image:         renderImageUpload,
      'image[]':     renderImageArrayUpload,
      video:         renderVideoUpload,
      audio:         renderAudioUpload,
      color:         renderColorInput,
      aspect_ratio:  renderAspectRatioGrid,
      seed:          renderSeedInput,
      model_selector:renderModelSelector,
    };
  }

  generate(config: ControlConfig, state: ValidatedState): ControlUI {
    const renderer = this.registry[config.type];
    if (!renderer) throw new Error(`Unknown control type: ${config.type}`);
    return renderer(config, state);
  }
}
```

## 8. Validation

Validation occurs at the `ValidatedState` boundary before `ApiPayload` construction. Two layers:

### 8.1 Per-Control Validation (inline)

Each `ControlUI.onValidate` runs on every change. Common rules:

```typescript
const RULES: Record<string, (v: unknown, meta: ControlMetadata) => string | null> = {
  required:  (v) => (!v || String(v).trim() === '') ? 'Required' : null,
  min:       (v, m) => (typeof v === 'number' && v < (m.min ?? 0)) ? `Min ${m.min}` : null,
  max:       (v, m) => (typeof v === 'number' && v > (m.max ?? Infinity)) ? `Max ${m.max}` : null,
  step:      (v, m) => {
    if (typeof v !== 'number' || !m.step) return null;
    return (v % m.step !== 0) ? `Must be multiple of ${m.step}` : null;
  },
  divisible64: (v) => (typeof v === 'number' && v % 64 !== 0) ? 'Must be divisible by 64' : null,
  custom:    (v, m, field) => field === 'width' ? validateDivisibleBy64(v) : null,
};
```

### 8.2 Cross-Field Validation (boundary)

After all controls update `ValidatedState.values`, the engine runs boundary checks:

```typescript
export function validateBoundary(state: ValidatedState, model: Model): ValidationError[] {
  const errors: ValidationError[] = [];

  // Image-to-image: require at least one uploaded image
  if (model.requiresImages) {
    const images = state.values.images_list ?? state.values.image_url;
    if (!images || (Array.isArray(images) && images.length === 0)) {
      errors.push({ key: 'image', message: 'At least one image is required for this model.' });
    }
  }

  // Prompt required unless model hasPrompt === false
  if (model.hasPrompt !== false && !state.values.prompt?.trim()) {
    errors.push({ key: 'prompt', message: 'Prompt is required.' });
  }

  // Request ID required for extension models
  if (model.requiresRequestId && !state.values.request_id?.trim()) {
    errors.push({ key: 'request_id', message: 'Request ID is required for this operation.' });
  }

  // Aspect ratio compatibility with width/height when both present
  if (state.values.aspect_ratio && state.values.width) {
    const [rw, rh] = state.values.aspect_ratio.split(':').map(Number);
    if (rw && rh && state.values.height) {
      const expectedHeight = Math.round((state.values.width / rw) * rh);
      if (Math.abs(state.values.height - expectedHeight) > 2) {
        errors.push({ key: 'height', message: `Height does not match aspect ratio ${state.values.aspect_ratio}.` });
      }
    }
  }

  return errors;
}
```

### 8.3 Clamping

Numeric inputs are clamped on blur (or on submit) to their declared `min`/`max`/`step`:

```typescript
function clamp(value: number, meta: ControlMetadata): number {
  let v = value;
  if (meta.min != null) v = Math.max(meta.min, v);
  if (meta.max != null) v = Math.min(meta.max, v);
  if (meta.step != null) v = Math.round(v / meta.step) * meta.step;
  return v;
}
```

## 9. Payload Builder

`ApiPayload` construction is deterministic: iterate `model.inputs` in insertion order, include only keys present in `ValidatedState.values`, and apply field-name overrides.

```typescript
export function buildApiPayload(state: ValidatedState, model: Model): ApiPayload {
  const payload: ApiPayload = { model: model.id };

  for (const [inputName, inputDef] of Object.entries(model.inputs)) {
    const apiField = inputDef.field || inputName;
    const value = state.values[inputName];

    if (value === undefined || value === null || value === '') continue;

    // Seed special case: -1 means "omit seed / random"
    if (inputName === 'seed' && value === -1) continue;

    // Image array special case: send images_list (primary) + image_url (backward compat)
    if (Array.isArray(value) && inputDef.type === 'image[]') {
      payload.images_list = value;
      payload.image_url = value[0];
      continue;
    }

    payload[apiField] = value;
  }

  return payload;
}
```

## 12. Implementation Constraints

- **No framework dependency for the engine itself.** Controls render to DOM via `document.createElement` / `innerHTML` patterns already used in `ImageStudio.js` and `VideoStudio.js`.
- **Tailwind CSS** is the styling layer. All engine controls use Tailwind utility classes; studios may extend via a `className` override in `ControlConfig`.
- **Event cleanup** must use the existing `Component.addEventListener` / `removeAllEventListeners` pattern from `src/components/base/Component.js` so controls can be mounted/unmounted without leaks.
- **State storage**: `ValidatedState` is a plain object. Studios may back it with their own state variables (e.g. `let guidanceScale = 7.5`) or use the engine's `ValidatedState` directly.
- **Model catalog integration**: `getEnrichedModels` in `src/lib/modelCatalog.js` returns models already matching the `Model` interface. The engine consumes them directly without transformation.
- **File size budget**: `ControlGenerator` + all renderers + `ValidatedState` + `buildApiPayload` should stay under ~400 lines total. If a studio needs custom controls beyond the built-in types, it registers a custom renderer at runtime.

## 13. Migration Path

1. **Phase 1**: Implement `ControlGenerator`, `ValidatedState`, `buildApiPayload`, and the 18 built-in renderers in `src/lib/controls/`.
2. **Phase 2**: Replace the inline parameter sections in `ImageStudio.js` with the engine (keep prompt bar, model selector, and generate button).
3. **Phase 3**: Replace the inline parameter sections in `VideoStudio.js` with the engine.
4. **Phase 4**: Migrate remaining studios (EditStudio, UpscaleStudio, LipSyncStudio, etc.) using the same pattern.
5. **Phase 5**: Move `Model.inputs` schema generation from the auto-generated `models.js` format into the backend catalog endpoint so `visibleWhen` / `validation` arrays are server-authoritative.
